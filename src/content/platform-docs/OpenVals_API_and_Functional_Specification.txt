OPENVALS
API & Functional Specification
Endpoint catalogue · Validation · Authorization · Error handling

1. Purpose
This document defines the functional expectations and API contract checklist for the OpenVals platform. It maps the principal user flows to API groups, expected validations, authorization requirements, and failure behavior. Endpoint paths are based on the supplied flow and must be reconciled with the actual FastAPI router definitions before implementation or client integration.
2. API Design Principles
Use a consistent `/api/v1` base path unless routing configuration specifies otherwise.
Authenticate protected routes and authorize every operation server-side.
Use tenant context derived from the authenticated session, not an untrusted organization ID alone.
Validate request bodies, query parameters, identifiers, amounts, and state transitions.
Return consistent machine-readable error codes and user-safe messages.
Use idempotency keys for payment creation, payment reconciliation, webhook processing, and other retryable writes.
Document pagination, sorting, filtering, and response schemas for list endpoints.

9. Recommended Response Shape
Use one consistent envelope across endpoints. The following is an illustrative contract only; align field names and status conventions with the existing API implementation.
{  "success": true,  "data": {},  "message": "Operation completed",  "request_id": "correlation-id"}
Illustrative error response:
{  "success": false,  "error": {    "code": "SEAT_LIMIT_EXCEEDED",    "message": "The organization has reached its seat limit."  },  "request_id": "correlation-id"}
10. Functional Rules by Domain
10.1 Authentication
Do not return password hashes or secrets.
Rate-limit login and reset initiation.
Use generic forgot-password responses.
Revoke all sessions after password reset.
Keep platform and organization authorization domains separate.
10.2 Subscription and Entitlements
Centralize state transition rules.
Calculate entitlement mode on the backend.
Validate seats and plan limits on every relevant write.
Do not activate from browser redirect alone.
Make payment and subscription reconciliation repeat-safe.
10.3 Invoices and Payments
Calculate totals server-side; never trust client totals.
Validate currency, invoice status, remaining balance, and payment reference.
Verify provider signatures and event identity.
Persist payment, invoice, subscription, and audit changes transactionally where possible.
Only reactivate subscriptions eligible under business policy.
10.4 Admin and Audit
Require explicit platform permission for each administrative action.
Record actor, target, action, timestamp, correlation ID, and before/after values where appropriate.
Audit offline payment reconciliation and subscription overrides.
Do not rely on frontend route guards as the security boundary.

13. Contract Confirmation Required
This specification is a functional baseline, not a claim that every listed route or HTTP method already exists. Before frontend integration, compare this catalogue with FastAPI routers and OpenAPI output. Confirm exact methods, payload schemas, response fields, status codes, permission identifiers, pagination conventions, and provider-specific webhook paths.
